# 智能虚拟列表组件

## 一、项目背景与问题（1-2分钟）

在业务场景中，我们遇到了一个典型的性能问题：费用列表数据量非常大（比如10万条记录），这导致了三个严重的性能瓶颈：

- 第一个问题就是接口会超时，一次性请求10万条数据，接口响应时间长达几十秒甚至超时
- 第二个问题就是页面卡顿，因为10万条数据需要渲染10万个DOM节点，会占用浏览器非常大的内存导致列表渲染卡顿以及滚动帧率非常低的问题
- 第三个问题就是资源的浪费，用户可能只看前40条数据，但请求了全部10万条

针对这些问题，我们前后端都设计了一些性能优化的策略，后端就是把这10w条数据分为了两个接口，一个ids接口存储全部的id、一个infos可以根据id去请求数据的详情。我设计并实现了一个**智能虚拟列表组件**，核心策略是：**虚拟滚动 + LRU缓存 + 智能预加载 + 批量加载**，以可见区域为中心向前后各扩展缓冲区，显著降低接口调用频率与渲染开销。

---

### 难点3：如何解决海量DOM渲染导致的性能问题？

首先来讲一下虚拟列表，虚拟列表主要就是来解决海量DOM渲染导致的性能问题。

10万条数据如果全部渲染，意味着10万个DOM节点，这会导致首屏渲染时间5-10秒、内存占用200MB以上、滚动帧率低于10FPS，页面甚至可能崩溃。

那我是怎么解决的呢？我采用了**虚拟滚动技术**，核心思想其实很简单：**只渲染用户能看到的20-30个DOM节点**。

具体实现上，我使用了 `@tanstack/react-virtual` 这个库：

```typescript
// 第一步：获取ID列表
const [ids, setIds] = useState([]);
useEffect(() => {
  fetch("/api/ids")
    .then((res) => res.json())
    .then((data) => {
      setIds(data); // [1, 2, 3, ..., 100000]
    });
}, []);

// 第二步：配置虚拟滚动（基于ID列表长度）
const rowVirtualizer = useVirtualizer({
  count: ids.length, // 总数据量
  estimateSize: () => rowHeight, // 每行高度
  overscan: 5, // 上下各多渲染5条作为缓冲
});

// 第三步：按需批量获取详细数据
const getItems = async ({ ids }) => {
  const response = await fetch("/api/data", {
    method: "POST",
    body: JSON.stringify({ ids }), // 批量请求：[1, 2, 3, ..., 40]
  });
  return response.json();
};
```

然后在渲染的时候，我用了绝对定位加transform的布局方式：

```typescript
<div style={{
  position: 'absolute',
  transform: `translateY(${virtualItem.start}px)`,
  height: `${virtualItem.size}px`,
}}>
  {item ? <RowData data={item} /> : <Skeleton />}
</div>
```

为什么要这样设计呢？绝对定位的好处是不需要频繁调整DOM结构，只需要计算transform值，浏览器渲染性能会很好。双接口策略的好处是首屏可以快速获取ID列表并渲染骨架屏，详细数据异步加载，用户体验会更好。缓冲区的作用是上下各预渲染5条，用户滚动时新的item已经准备好了，避免出现空白。

最终的实际效果是：

- DOM节点从10万降到20-30个，减少了99.97%
- 内存占用从200MB降到5MB，减少了97.5%
- 首屏渲染从5-10秒降到500毫秒以内
- 滚动帧率从低于10FPS提升到稳定60FPS

### 难点2：如何避免重复请求和控制内存？

虚拟列表解决了DOM渲染的问题，**下一步就是数据从哪里来**。

在实际使用中，我们遇到了**来回滚动时重复请求相同数据**的问题：每次滚动都触发加载导致加载状态频繁闪烁，如果把所有请求过的数据都缓存起来，内存占用会越来越高。虽然我们通过批量请求（每次40条）减少了请求次数，但还需要解决重复加载和内存控制的问题。

所以我设计了一个**LRU智能缓存**来解决这些问题。LRU就是Least Recently Used，最近最少使用的意思。
LRU简单来说就是当我们的缓存满了的时候，他会删除最近最少被使用的数据。
为什么选择LRU呢？首先它符合用户行为，用户滚动时最近看到的数据很可能再次访问。比如用户从第1条滚动到第1000条的时候，他很可能会回头看第950条，也就是最近访问过的数据。其次性能优秀，所有操作都是O(1)时间复杂度。最后内存可控，缓存大小固定，默认1000条，自动清理，不会内存泄漏。

具体实现上，我利用了**JavaScript中Map的有序性特点**。Map会按照插入顺序保存键值对，所以我可以用它来实现LRU：最近使用的数据保留在缓存末尾，最久未使用的数据排在缓存开头，缓存满时淘汰开头的数据。

```typescript
// 访问数据时：删除后重新插入，移到末尾（标记为最近使用）
const getData = (id) => {
  const item = cache.get(id);
  if (item) {
    cache.delete(id);
    cache.set(id, item); // 重新插入，移到末尾
  }
  return item;
};

// 写入数据时：容量满时删除第一个（最久未使用）
const setData = (id, item) => {
  if (cache.size >= maxSize) {
    const oldestKey = cache.keys().next().value; // 获取第一个key
    cache.delete(oldestKey); // 删除最久未使用的
  }
  cache.set(id, item);
};
```

除了缓存，我还设计了**加载状态追踪**来避免重复请求。当收到一批要请求的ID后，我会先把它们标记为loading状态，这样在请求返回之前，如果用户又滚动到这些位置，就不会重复发起请求，等请求返回之后再把数据写入缓存。

```typescript
const fetchAndCacheData = async (items) => {
  const idsToFetch = items.map((item) => item.id);

  // 1. 先标记为加载中，避免重复请求
  idsToFetch.forEach((id) => loadingSet.add(id));

  // 2. 批量请求
  const itemsData = await getItems({ ids: idsToFetch });

  // 3. 写入LRU缓存
  itemsData.forEach((item) => setData(item.id, item));

  // 4. 清除加载状态
  idsToFetch.forEach((id) => loadingSet.delete(id));
};
```

加载状态判断的逻辑是这样的：

| 状态     | hasData | isLoading | 操作                   |
| -------- | ------- | --------- | ---------------------- |
| 已缓存   | ✅      | ❌        | 不加载（直接使用）     |
| 正在加载 | ❌      | ✅        | 不加载（避免重复请求） |
| 需要加载 | ❌      | ❌        | 加载（加入批量请求）   |

实际效果是：来回滚动时缓存命中率超过90%，接口调用频率降低80%以上，用户体验流畅，加载状态很少出现。

### 难点1：如何智能地决定加载哪些数据？

> 如果是刚进入页面的话，就加载前40条，滚动到35条的时候，就继续加载下面的41-80条
> 如果滚动的特别快，直接滚动到中间第5000条的话，我会先优先加载当前可视区（虚拟列表的第三方库会抛给我一个方法，能获取到当前可视区dom的索引和id）的数据，然后根据滚动方向扩展到40条
> 有了LRU缓存之后，接下来的问题是：**每次请求40条，但具体应该加载哪40条呢？**

最简单的做法是普通懒加载：首屏进来加载第1-40条，当我滚动到第35条的时候，加载第41-80条，从上往下慢慢滚慢慢分批加载。但是用户很有可能直接从第1条拖动滚动条跳到第5000条，这时候普通懒加载就不行了，因为中间的数据都没加载过，我不可能把中间用户滚动跳过不需要看的几千条都加载一遍。

所以我设计了一个**智能加载策略**，核心思路是：**优先加载当前可视区的数据，然后再向滚动方向扩展预加载**。

虚拟列表库会告诉我当前可视区有哪些DOM，比如当前显示的是第5000-5020条。那我就会先检查这20条里面哪些没有缓存，优先加载它们，然后再向滚动方向继续收集，凑够40条一起请求。

具体实现分三步：

**第一步是判断滚动方向并确定检查范围**。我设计了一个触发阈值机制，不是每次滚动都触发请求，而是只在接近未缓存边界时才触发。

判断滚动方向有以下几种方法：

**方法1：基于scrollTop的变化（本项目采用）**

```typescript
const handleScroll = () => {
  const currentScrollTop = container.scrollTop;
  if (currentScrollTop > lastScrollTop) {
    scrollDirection = "down"; // 向下滚动
  } else {
    scrollDirection = "up"; // 向上滚动
  }
  lastScrollTop = currentScrollTop;
};
```

这种方式实现简单，兼容性好，但需要维护一个 `lastScrollTop` 状态。

**方法2：基于wheel事件的deltaY**

```typescript
const handleWheel = (e: WheelEvent) => {
  if (e.deltaY > 0) {
    scrollDirection = "down"; // 向下滚动
  } else {
    scrollDirection = "up"; // 向上滚动
  }
};
```

这种方式响应更快，可以更早地预知滚动方向，适合预加载优化，但仅适用于鼠标滚轮，触屏设备不支持。

**方法3：基于虚拟列表库提供的API**

```typescript
// @tanstack/react-virtual 提供了虚拟滚动信息
const virtualizer = useVirtualizer({
  count: ids.length,
  getScrollElement: () => parentRef.current,
});

// 通过 virtualizer 的状态变化推断方向
const lastRangeRef = useRef({ start: 0, end: 0 });
useEffect(() => {
  const currentRange = {
    start: virtualizer.range?.startIndex ?? 0,
    end: virtualizer.range?.endIndex ?? 0,
  };
  const lastRange = lastRangeRef.current;

  if (currentRange.start > lastRange.start) {
    scrollDirection = "down";
  } else if (currentRange.start < lastRange.start) {
    scrollDirection = "up";
  }
  lastRangeRef.current = currentRange;
}, [virtualizer.range]);
```

这种方式更符合虚拟列表的语义，通过可视范围的变化判断方向，但需要依赖具体的虚拟列表库。

本项目最终选择了**方法1（scrollTop方式）**，原因如下：

1. **兼容性好**：同时支持鼠标滚轮、触屏拖拽、键盘滚动等各种交互方式
2. **实现简单**：只需要一个状态变量，代码简洁易维护
3. **性能足够**：对于列表滚动场景，scrollTop的更新频率已经满足需求

确定滚动方向后，我设计了触发阈值机制：

```typescript
const threshold = Math.floor(pageSize / 8); // 触发阈值，约5条

// 根据滚动方向确定检查范围
if (scrollDirection === "down") {
  // 向下滚动：检查可视区 + 底部阈值
  checkStart = visibleStart;
  checkEnd = Math.min(ids.length, visibleEnd + threshold);
} else if (scrollDirection === "up") {
  // 向上滚动：检查顶部阈值 + 可视区
  checkStart = Math.max(0, visibleStart - threshold);
  checkEnd = visibleEnd;
}

// 检查范围内是否有未缓存数据，没有则不触发请求
```

**第二步是收集未缓存的ID**。因为可视区的20条加上滚动方向后面的20条，之前可能已经请求过了，所以要先过滤掉已缓存的。比如用户从第5000条滚回第4990条，这时候4990-5010可能都已经缓存了，就不需要再请求。

收集策略是这样的：先收集可视区内的未缓存ID，如果不够40条，再向滚动方向继续收集。如果滚动方向已经没有更多数据了，就往反方向补充。

```typescript
// 第一步：收集可视区内的未缓存ID（限制在可视区边界内）
const visibleUncached = collectUncachedIds(
  visibleStart,
  "forward",
  pageSize,
  visibleEnd
);

// 第二步：如果不够pageSize，向滚动方向继续收集
if (visibleUncached.length < pageSize) {
  const remaining = pageSize - visibleUncached.length;

  if (scrollDirection === "up") {
    // 向上滚动：从可视区顶部向前补充（如果前面没了，往后补充）
    const preItems = collectUncachedIds(
      visibleStart - 1,
      "backward",
      remaining
    );
    uncachedItems = [...preItems, ...visibleUncached];
  } else {
    // 向下滚动：从可视区底部向后补充（如果后面没了，往前补充）
    const postItems = collectUncachedIds(visibleEnd, "forward", remaining);
    uncachedItems = [...visibleUncached, ...postItems];
  }
}
```

这里有一个关键设计是**边界限制**。collectUncachedIds函数支持边界参数，确保不会越界收集：

```typescript
const collectUncachedIds = (startIndex, direction, count, boundary?) => {
  const result = [];
  let index = startIndex;

  while (result.length < count) {
    // 边界检查：到达boundary就停止
    if (direction === "forward" && boundary !== undefined && index >= boundary)
      break;
    if (direction === "backward" && boundary !== undefined && index < boundary)
      break;

    const id = ids[index];
    // 同时检查缓存状态和加载状态
    if (!hasData(id) && !isLoading(id)) {
      result.push({ id, index });
    }
    index += direction === "forward" ? 1 : -1;
  }
  return result;
};
```

举个对比的例子来说明边界限制的作用。假设用户向上滚动到位置100-107，其中100-104已缓存，105-107未缓存。

**旧方案（无边界限制）**：

```
收集可视区：从100向后搜索，跳过已缓存的100-104
继续搜索到108、109...可能收集到后面不需要的数据
结果：收集了向下方向的数据，但用户在向上滚动！
```

**新方案（边界限制 + 方向感知）**：

```
第一步：收集可视区100-107（边界限制在107）
  → 只收集到105、106、107（3个）
第二步：不够40个，向上扩展
  → 从99向前收集37个
结果：[63-99] + [105-107] = 40个，全部是正确方向的数据
```

**第三步是批量请求接口并写入缓存**：

```typescript
const fetchAndCacheData = async (items) => {
  const idsToFetch = items.map((item) => item.id);

  // 1. 标记为加载中（显示skeleton，避免重复请求）
  idsToFetch.forEach((id) => loadingSet.add(id));

  // 2. 批量请求（最多40条）
  const itemsData = await getItems({ ids: idsToFetch });

  // 3. 写入LRU缓存
  itemsData.forEach((item) => setData(item.id, item));

  // 4. 清除加载状态
  idsToFetch.forEach((id) => loadingSet.delete(id));
};
```

再举个完整的例子来说明整个加载流程：

```
用户向下滚动到位置100-107（可见范围8条）
↓
检查范围：100-112（可视区 + 阈值5条）
↓
发现有未缓存数据，触发加载
↓
第一步：收集可视区100-107内的未缓存ID（假设3个）
↓
第二步：不够40条，从108向后继续收集37个
↓
最终请求：可视区3条 + 后续37条 = 40条
↓
请求返回后写入LRU缓存，触发UI重新渲染
```

这里可能有人会问，为什么不用React Query呢？React Query虽然是一个优秀的数据获取库，但在虚拟滚动的场景下存在一些局限性。

**第一个问题是不支持智能部分缓存**。React Query的缓存是基于完整queryKey的，不支持跨查询的部分数据重用：

```typescript
// 第一次请求
queryKey: ["items", [1, 2, 3, 4]]; // 缓存了 id: 1,2,3,4 的数据

// 第二次请求
queryKey: ["items", [2, 3, 4, 5]]; // 期望：重用 2,3,4，只请求 5
```

实际情况是，`['items', [1,2,3,4]]` 和 `['items', [2,3,4,5]]` 是两个完全不同的缓存键，第二次请求会重新获取2,3,4,5的所有数据，不会重用已缓存的2,3,4，导致大量重复请求。

**第二个问题是双向滚动场景下的并发问题**。向下滚动的时候，useInfiniteQuery的"加载更多"模式可以正常工作，但向上滚动需要加载之前的数据，React Query没有内置的"加载更少"机制，从下往上滚会触发很多次单个ID的请求，导致大量接口并发。

**第三个问题是无法精确控制加载范围**。我们的场景需要根据滚动位置动态计算需要加载的数据范围，每次请求当前行前后未被请求的20条数据，而不是固定的"下一页"，还需要智能识别已缓存的数据避免重复请求。React Query的useInfiniteQuery更适合分页场景，不太适合虚拟滚动的随机访问模式。

**第四个问题是缓存策略不够灵活**。React Query的缓存策略基于查询key，我们的场景需要基于索引范围的精细控制，自实现LRU缓存更符合滚动场景的访问模式。

关于pageSize的选择，我整理了一个策略表：

| 数据大小    | 网络状况 | 推荐pageSize | 说明                     |
| ----------- | -------- | ------------ | ------------------------ |
| 小（<1KB）  | 快       | 60-100       | 单次请求快，可以多加载   |
| 小（<1KB）  | 慢       | 40-60        | 平衡单次请求时间和加载量 |
| 大（>10KB） | 快       | 20-40        | 避免单次数据太大         |
| 大（>10KB） | 慢       | 10-20        | 减少单次请求时间         |

## 二、架构设计（2-3分钟）

接下来说一下整体的架构设计。我采用了清晰的三层架构，职责分离：

```
┌─────────────────────────────────────┐
│         UI 层 (index.tsx)           │
│  - 虚拟滚动容器                     │
│  - 滚动事件监听                     │
│  - 滚动方向判断                     │
│  - 渲染 RowComponent                │
└─────────────────────────────────────┘
              │ 使用
              ▼
┌─────────────────────────────────────┐
│    数据加载层 (useSmartDataLoader)  │
│  - 计算加载范围                     │
│  - 检查未缓存数据                   │
│  - 收集需要加载的ID                 │
│  - 批量请求接口                     │
└─────────────────────────────────────┘
              │ 使用
              ▼
┌─────────────────────────────────────┐
│      缓存层 (useLRUCache)           │
│  - LRU缓存管理                      │
│  - 加载状态追踪                     │
│  - 版本触发重渲染                   │
└─────────────────────────────────────┘
```

数据流是这样的：

```
用户滚动
  ↓
【UI层】捕获滚动事件，判断滚动方向，更新可见范围
  ↓
【数据加载层】检查触发阈值范围内是否有未缓存数据
  ↓
【数据加载层】两步收集：可视区优先 → 向滚动方向扩展
  ↓
【数据加载层】批量请求接口
  ↓
【缓存层】写入LRU缓存，更新加载状态，触发version更新
  ↓
【UI层】重新渲染，显示真实数据
```

核心职责划分是这样的：

| 层级       | 职责                               | 关键函数/状态                                              |
| ---------- | ---------------------------------- | ---------------------------------------------------------- |
| UI层       | 渲染、事件监听、滚动方向判断       | handleScroll, scrollDirectionRef, visibleRangeRef          |
| 数据加载层 | 触发阈值检查、两步收集ID、批量请求 | handleScrollTrigger, collectUncachedIds, fetchAndCacheData |
| 缓存层     | LRU缓存管理、加载状态追踪          | hasData, isLoading, setDataBatch, version                  |

这个架构的优势在于：第一，职责清晰，每一层只负责自己的事情，便于维护和测试；第二，可扩展性强，可以轻松替换数据源或修改加载策略；第三，可复用性高，每个Hook都可以独立使用。

## 四、可能的追问与回答

### Q1：为什么选择LRU而不是其他缓存策略？

我选择LRU是因为它最符合列表滚动的使用场景。

首先它符合用户行为，用户滚动时最近看到的数据很可能再次访问，比如来回滚动查看对比，而最久未看到的数据很可能不会再访问。其次性能优秀，所有操作都是O(1)时间复杂度，实现简单。最后内存可控，缓存大小固定，自动清理，不会内存泄漏。

相比之下，FIFO（先进先出）可能淘汰用户正在查看的数据，导致频繁重新加载；LFU（最不经常使用）需要维护访问频率，实现复杂，且在滚动场景中不如LRU合适。

### Q2：pageSize是如何选择的？

pageSize的选择需要权衡两个因素：单次请求时间和加载量。

数据小且网络快的时候，选择60-100，单次请求快可以多加载；数据大或网络慢的时候，选择10-40，减少单次请求时间。

我默认设置40是在常见场景下的平衡值，既能减少请求次数（相比单条请求减少97.5%），又不会让单次请求时间太长（通常小于1秒）。实际项目中可以根据数据大小和网络状况动态调整。

### Q3：虚拟滚动有什么局限性？

虚拟滚动虽然性能好，但也有局限性。

第一，需要固定或可预测的行高，动态高度需要额外处理比如测量高度。第二，不适合复杂交互，比如多选、批量编辑等操作会比较复杂。第三，滚动到指定位置需要额外处理，需要计算位置并滚动。第四，不适合数据频繁变化的场景，缓存会频繁失效。

对于这些场景，可以考虑使用动态高度测量（如@tanstack/react-virtual的动态高度支持），简化交互逻辑或者使用分页加载代替虚拟滚动，对频繁变化的数据采用实时更新策略。

### Q4：如果后端不支持批量接口怎么办？

如果后端不支持批量接口，有两个方案。

**方案1是前端并行请求**：

```typescript
const promises = uncachedIds.map((id) => fetchItem(id));
const results = await Promise.all(promises);
```

虽然不如真正的批量接口快，但比串行请求快很多。

**方案2是建议后端增加批量接口**。在大数据量场景下，批量接口几乎是必需的，可以减少网络开销、降低服务器压力、提升响应速度。可以在技术评审时提出这个需求，通常后端团队会理解并支持。

### Q5：这个方案的适用场景有哪些？

这个方案适用于以下场景：

✅ **适合的场景**：大数据量列表（1万条以上）、数据不会频繁变化（或者变化后可以接受短暂的不一致）、用户主要是浏览数据（而不是频繁编辑）、需要流畅的滚动体验。

❌ **不适合的场景**：数据量很小（虚拟滚动的优势不明显，反而增加复杂度）、数据频繁变化（缓存会频繁失效）、需要对列表进行复杂操作（比如多选、批量编辑、拖拽排序）、需要实时更新数据（比如聊天记录、股票行情）。

对于不适合的场景，可以考虑：小数据量直接渲染即可，频繁变化使用实时更新策略（WebSocket），复杂操作使用分页加载或简化交互。

## 五、总结与收获（1分钟）

通过这个项目，我深入理解了几个方面。

**性能优化的核心思路**：减少DOM渲染（虚拟滚动）、减少网络请求（批量加载 + 缓存）、控制内存占用（LRU缓存）、优化用户体验（智能预加载）。

**调试和优化经验**：从实际性能问题出发不要过度优化、关注用户体验不仅仅是技术指标、架构设计要考虑可维护性和可扩展性。
