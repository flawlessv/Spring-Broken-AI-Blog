# 在 Markdown 编辑器中实现 AI Tab 补全功能

## 一、项目背景与问题（1-2分钟）

大家好，我今天要讲的是如何在 Markdown 编辑器中实现类似 GitHub Copilot 的 AI Tab 补全功能。

大致的一个交互就是用户在编辑器中输入文本时，系统能够自动提取光标前的文本作为上下文，调用 AI API 生成补全建议，然后以灰色斜体文本的形式显示在光标位置。用户可以通过 Tab 键接受补全

这个功能看起来简单，但实际上有几个核心挑战：

- 第一个问题是**非侵入式显示**。补全建议不能直接写入文档，否则会影响撤销栈，产生数据污染。比如用户不接受补全，但补全已经写入文档了，撤销起来就很麻烦
- 第二个问题是**实时响应**。需要监听用户输入，及时触发补全请求，但又不能太频繁导致 API 调用过多
- 第三个问题是**异步竞态处理**。AI API 调用是异步的，用户可能在 API 返回前继续输入，这时候补全建议可能显示在错误的位置
- 第四个问题是**位置同步**。要确保补全建议始终显示在正确的光标位置

## 二、解决方案演进（2-3分钟）

### 难点1：最初的两次尝试为什么失败了？

最开始，我想的是使用css的方式在光标的后面叠加一个透明的 DOM 层，通过绝对定位来显示补全建议。
但是会有一些问题，比如用户输入 `123|45`，光标在中间，我需要把光标后面的的文字往后移动空间来给tab展示的内容进行让位，需要精确光标后文本的长度，，还要考虑字体、字号、等等。更麻烦的是，所以这个方案虽然思路简单，但实现复杂，维护成本高，而且难以处理各种边界情况。

既然叠加层不行，我就想，那直接把补全建议插入到文档中，用户不接受时执行撤销操作，不就行了吗？

这个方案听起来更简单，但也有问题。第一个问题是撤销栈污染，每次补全都会产生一次 插入 记录，用户需要按多次 Ctrl+Z 才能撤销。第二个问题是数据污染，如果补全插入后用户直接关闭页面或者网络卡顿，再打开时无法区分是用户输入还是 AI 补全。

所以这两个方案都不行。

**解决方案**：通过学习 VSCode，我发现了**虚拟文本机制**。

本来想看下 Cursor 怎么实现的，但是 Cursor 不开源，我就去看了 VSCode 的实现。

VSCode 中的补全建议是灰色的、半透明的，不会影响文档内容，只有按 Tab 确认后才会写入。这种实现方式完美解决了我们遇到的问题。

在 VSCode 中，无论是 AI 补全（GitHub Copilot）还是传统的代码提示补全，都通过**虚拟文本**机制实现。虚拟文本是一种**不实际写入文档、仅在编辑器界面渲染显示**的文本内容。它有三个核心特性：

- **非侵入性**：虚拟文本不会被保存到文件中，不会占用真实的文档字符位置，只是编辑器在界面上的"视觉层叠加"
- **动态绑定**：虚拟文本和光标位置、代码上下文绑定，会随着光标移动、代码修改实时更新或消失
  VSCode 虚拟文本的实现，核心基于**编辑器的分层渲染架构**和**文本模型与视图分离**的设计理念。VSCode 的编辑器内核基于 Monaco Editor，核心设计是**模型-视图分离**。模型层存储真实文档内容，包括字符、行数、偏移量等，文件的读写、保存、编译都基于这个层。视图层将模型层内容渲染到屏幕上，处理光标位置、滚动、高亮等视觉交互。

通过学习 VSCode 的实现原理，我认识到：

1. 必须使用非侵入式渲染，补全建议不能写入文档模型；
2. 需要类似虚拟文本的机制，装饰器/装饰机制，在视图层叠加显示，不影响文档结构；
3. 需要事件监听，实时响应输入、光标移动等操作；
4. 需要状态管理，管理补全建议的内容、位置、显示状态。

这时候我就面临一个选择：是手动实现虚拟文本效果，还是直接用 ProseMirror 的 Decoration API？

如果要手撕的话，有一个现成的参考案例：`prosemirror-dropcursor` 插件。这个插件在拖拽时显示一个插入位置指示器，它就是用纯 DOM 方式实现的。

具体思路是这样的：首先创建一个绝对定位的 `div` 元素作为补全文本容器，然后利用 ProseMirror 的 `coordsAtPos` API 将文档位置转换为屏幕坐标。`coordsAtPos` 会帮我们处理好字体、行高、缩进等各种复杂因素，返回准确的 `{left, top, right, bottom}` 坐标。有了这些坐标，就可以直接设置 `div` 的 `style.left` 和 `style.top`，把虚拟元素显示在正确位置。

当用户输入或光标移动时，重新调用 `coordsAtPos` 获取新坐标，更新虚拟元素的位置。这个方案的好处是不依赖 Decoration API，完全由自己控制渲染逻辑。`prosemirror-dropcursor` 就是这样实现的，而且效果很好。

但这个方案也有一个潜在问题：需要手动处理很多边界情况。比如文档滚动时要同步更新位置，窗口缩放时要重新计算坐标，编辑器容器有 padding 或 border 时要考虑偏移量。而且 `coordsAtPos` 返回的是相对于视口的坐标，需要转换成相对于编辑器容器的坐标。这些都是体力活，虽然不难，但容易出 bug。

相比之下，使用 Decoration API 就简单多了。它本质上是一个封装好的"坐标计算 + DOM 渲染"工具，我们只需要告诉它"在什么位置显示什么内容"，剩下的位置同步、滚动更新、坐标转换都由框架处理。这就是为什么最终选择 Decoration 机制——不是因为手撕做不到，而是因为框架已经提供了更可靠的方案。

**为什么选择 ProseMirror？**

我们的编辑器基于 Tiptap，而 Tiptap 是基于 ProseMirror 的。ProseMirror 提供了三个核心能力来满足我们的诉求：

第一个是 **Decoration 机制**，用于在视图层叠加显示虚拟内容。Decoration 可以在文档的某个位置创建一个只存在于视图层的 DOM 元素，它不会被写入文档模型，也不会影响撤销重做。这正是我们实现"灰色斜体补全文本"的基础。

第二个是 **Plugin 系统**，让我们能够实现自己的业务逻辑。Plugin 允许我们创建一个独立的状态空间来存储补全信息，并且提供一个 `apply` 方法，在每次文档变化时被调用。在这个方法里，我们自己实现了一套判断逻辑：根据操作类型的不同，执行不同的处理。比如用户输入文本时触发补全请求，用户按 Tab 时接受补全，用户按 Esc 时取消补全。

第三个是 **事务机制和事务元数据**。在 ProseMirror 中，所有的文档变化都通过"事务"进行，事务可以携带元数据来传递额外的信息。我们利用事务元数据来标记不同的操作类型，这样在 `apply` 方法中就能知道当前这个变化是由什么操作触发的。比如我们定义了 `accept` 表示用户接受补全，`clear` 表示用户取消补全，`update` 表示 AI 返回了补全建议。通过这些标记，`apply` 方法就能区分不同场景，执行相应的逻辑。

接下来我按数据流的方式讲一下具体实现。整个流程可以分成四个环节：

**第一个环节是状态存储**。我们需要存储两个信息：补全内容是什么，以及应该显示在哪里。我们利用 Plugin 提供的独立状态空间来存储 `{ suggestion, position }`。这个状态和文档状态是完全分离的，所以更新补全状态不会触发文档变化，也不会影响撤销重做。

**第二个环节是响应用户操作**。当用户在编辑器中进行任何操作时，`apply` 方法都会被调用。我们首先检查事务的元数据，判断操作类型：如果元数据是 `accept`，说明用户按了 Tab 接受补全，我们清除补全状态；如果元数据是 `clear`，说明用户按了 Esc 取消补全，我们也清除状态；如果元数据是 `update`，说明 AI 返回了补全建议，我们更新状态；如果没有任何元数据，说明是用户在输入文本，这时我们启动一个 500ms 的防抖定时器，等用户停止输入后再调用 AI API。

**第三个环节是显示补全建议**。AI 返回补全后，我们创建一个带有 `update` 元数据的新事务来更新插件状态。这时 ProseMirror 会调用 `decorations` 方法进行渲染。在这个方法里，我们做两件事：第一，检查有没有补全建议，没有就返回空；第二，校验光标位置，只有当光标还在原位置时才显示补全，避免显示过期的建议。校验通过后，我们创建一个灰色斜体的 `span` 元素，设置 `pointer-events: none` 让用户无法选中，然后通过 `Decoration.widget` 挂在光标位置。这个装饰元素会在视图层渲染，但不会写入文档。

**第四个环节是用户接受或取消补全**。我们监听了 Tab 和 Esc 两个快捷键。如果用户按 Tab，我们就接受补全，通过事务把补全文本插入到文档中，并设置 `accept` 元数据。如果用户按 Esc，我们只需要创建一个带有 `clear` 元数据的事务，补全就会消失。这两个操作都会触发 `apply` 方法，但因为有了元数据标记，`apply` 方法能够识别这是用户操作而不是新的输入，所以不会再次触发 API 请求。

## 这样就形成了一个完整的闭环：用户输入 → 停止输入后触发 API → 显示补全 → 用户接受或取消 → 清除状态。整个过程中，补全建议始终是虚拟的，只有用户按 Tab 确认后才会真正写入文档。

### 难点2：其他实现细节

**防抖机制**：如果用户在AI 补全建议生成的过程过继续输入了新的内容或者光标的位置变化了，就要把之前生成建议的请求给取消掉

防抖：只有光标位置不变xxms后才去生成补全建议

**双重位置校验**：AI API 调用是异步的，用户可能在 API 返回前继续输入。

**光标位置同步**：在 `decorations` 方法中校验光标位置，位置不一致时不显示装饰；在 `apply` 方法中检测文本变化，如果有变化且不是补全操作，则清除补全。这样虚拟文本不会让光标"跳"过去，用户体验非常流畅。

**避免循环触发**：使用事务元数据传递信息，区分"用户输入"和"补全更新"。用户按 Tab 接受时设置 `ai-completion-accept` 元数据，按 Esc 取消时设置 `ai-completion-clear` 元数据，API 返回时设置 `ai-completion-update` 元数据。这样避免了补全更新直接修改文档导致的无限循环。

## 三、整体架构（1分钟）

基于 ProseMirror 的插件系统，我实现了 AI 补全扩展。整个流程是这样的：

```
用户输入 → ProseMirror 状态变化 → apply 方法
  ↓
检查元数据
  ├─ 有清除/接受/更新元数据 → 直接更新状态
  └─ 无元数据 → 检查文本变化
      ↓
    通过边界检查 → 设置防抖定时器（500ms）
      ↓
    调用 AI API → 位置校验
      ↓
    更新插件状态 → decorations 渲染 → 显示补全建议

用户按 Tab → 接受补全 → 插入文本 → 清除状态
用户按 Esc → 清除补全状态
```

简单来说就是：用户输入文本后，触发 `apply` 方法，检查元数据，如果没有元数据就检查文本变化，通过边界检查后设置防抖定时器，延迟 500ms 后调用 AI API，API 返回后进行位置校验，校验通过后更新插件状态，`decorations` 方法渲染补全建议，显示在光标位置。

用户按 Tab 时，接受补全，插入文本，清除补全状态。用户按 Esc 时，清除补全状态。

**性能优化方面**，我做了以下优化：

1. **防抖机制**：减少 API 调用次数，延迟 500ms 避免频繁请求
2. **位置校验**：避免无效的状态更新
3. **边界检查**：提前过滤不需要补全的场景，比如代码块、选中状态等
4. **静默失败**：API 错误不影响用户编辑体验，不会弹出错误提示

这个架构的优势：

- **非侵入式**：补全建议不影响文档内容
- **性能优化**：防抖 + 位置校验，减少无效请求
- **用户体验**：流畅的交互，不干扰正常编辑

## 五、技术亮点

### 为什么选择 Decoration 而不是其他方案？

**相比 DOM 叠加层**：

- 不需要手动计算像素位置
- 不受字体、浏览器差异影响
- 自动跟随文档滚动

**相比直接插入文本**：

- 不会污染撤销栈
- 不会污染文档内容
- 用户拒绝时不产生副作用

## 六、可能的追问与回答

### Q1：防抖时间为什么选择 500ms？

500ms 是一个经过权衡的值。太短会导致用户还在输入时就触发 API 请求，浪费资源；太长会让用户觉得响应慢，体验不好。500ms 刚好是用户输入一个词或短语的间隔。

### Q2：如何处理 AI API 调用失败的情况？

采用静默失败策略。如果 API 调用失败，不显示任何错误提示，用户可以继续正常编辑。AI 补全只是辅助功能，不应该因为补全失败而干扰用户的编辑体验。

### Q3：如果要支持多行补全，需要做哪些修改？

多行补全需要修改几个地方：

1. Decoration 渲染：当前是创建一个 span 元素，多行补全需要创建多个元素或使用 pre 标签
2. 位置计算：需要考虑多行文本插入后光标的最终位置
3. 样式处理：多行补全的样式需要特殊处理，比如缩进、行高等

核心逻辑不需要大改，主要是渲染层的调整。

### Q4：这个方案的适用场景？

**适合**：Markdown 编辑器、富文本编辑器、代码编辑器（基于 ProseMirror/CodeMirror）、需要 AI 辅助写作的场景

**不适合**：纯文本输入框（可以用更简单的 DOM 方案）、实时协作编辑器（需要处理多人光标同步）、移动端（键盘交互方式不同）
