# AI 博客项目面试问题逐字稿（20 题，详细版）

> 使用方式：每题先背“主回答”，如果面试官继续追问，再接“可补充”部分。

## 1. 为什么选择 Next.js 15 做全栈一体，而不是前后端分离？

主回答：  
我这个项目是内容型博客，既要保证 SEO 和首屏体验，又要快速迭代 AI 功能。选 Next.js 15 做全栈一体，最大的收益是“同一套代码同时解决页面渲染和后端接口”，开发效率高，联调成本低。比如前台页面、AI 流式接口、内容管理接口都在一个仓库里，接口改动和页面改动可以同步上线，不需要跨项目协调。  
另外 Next.js 对流式场景也比较友好，服务端可以直接返回 `ReadableStream`，很适合做 SSE 实时输出。对我们这种中小团队来说，这种架构能在保证体验的前提下，把交付速度提上来。

可补充：  
如果是超大团队、业务边界非常清晰，前后端分离也成立；但这个项目更重“快速验证和持续迭代”，全栈一体性价比更高。

## 2. 这个项目从“用户输入”到“AI 输出”完整链路是怎样的？

主回答：  
完整链路我一般分 8 步讲：  
第一步，用户在前台输入问题，前端做基础校验并截取最近历史消息。  
第二步，前端发起 `/api/ai/companion/chat/stream` 请求。  
第三步，服务端校验 `mode/message/history`，过滤非法角色和异常长度。  
第四步，服务端准备上下文信息和系统提示词，组装最终 `messages`。  
第五步，调用模型流式接口，收到 chunk 后转换成 SSE 事件。  
第六步，前端消费 SSE，先进入缓冲区，再按批次刷新 UI。  
第七步，流式阶段先纯文本展示，`done` 后再走 Markdown 渲染。  
第八步，异常统一走兜底分支，保证会话不崩、用户有反馈。  
这样做的目标是把“实时性、稳定性、可读性”同时兼顾。

可补充：  
我会强调“输入校验、流式过程、收尾兜底”这三段，因为面试官一般会追问这三块的细节。

## 3. Copilot 的异步竞态具体怎么出现？如何避免旧请求覆盖新状态？

主回答：  
竞态场景很典型：用户连续输入时会触发多次请求，旧请求可能比新请求晚返回。如果不做控制，旧结果就会覆盖新结果，导致补全建议“倒退”。  
我的处理是三层：  
第一层是防抖，先减少请求数量。  
第二层是请求版本号或时间戳，只允许“当前最新请求”更新 UI。  
第三层是中断机制，新的输入到来时主动取消过期请求。  
这样做后，即使网络抖动，也能保证展示的是最新上下文对应的补全结果。

可补充：  
可以举一个时间线例子：`request-A` 在 t1 发出，`request-B` 在 t2 发出，但 A 在 t3 才返回；如果没有版本判断，A 会把 B 的结果覆盖掉。

## 4. 防抖参数怎么定？如何平衡响应速度和建议质量？

主回答：  
我不是固定写死某个值，而是从一个合理区间起步，再结合数据调整。  
通常先用 300 到 500ms 作为初始区间，观察三个信号：  
第一，用户体感是否“跟手”；  
第二，请求频率是否过高；  
第三，建议命中率和可用率是否稳定。  
如果防抖过短，会产生大量无效请求；如果过长，用户会感觉迟钝。最后我会选“输入稍停就触发”的节奏，目标是既不过度打断，也不过度等待。

可补充：  
我会把输入场景拆成短句、长段、连续删改三类分别看数据，再做统一参数。

## 5. 前台对话为什么选择 SSE + ReadableStream，而不是 WebSocket？

主回答：  
因为这个场景本质是“服务端单向持续推送文本”，SSE 天然适配。  
SSE 基于 HTTP，接入简单，和现有网关、鉴权、日志体系兼容好；前端用 `fetch + ReadableStream` 可以带请求体，满足我们需要传历史消息和模式参数的需求。  
WebSocket 更适合强双向高频交互，比如协同编辑、实时白板。我们这里主要是“请求一次，服务端持续返回”，SSE 更轻、实现复杂度更低。

可补充：  
如果未来要做“服务端主动推送任务状态、多人实时协同”，再考虑 WebSocket 会更合适。

## 6. 高频流式返回时，你定位到的主要性能瓶颈是什么？

主回答：  
我定位到三个核心瓶颈：  
第一，SSE 事件风暴。模型按 token 回调时，如果每个 token 都发一帧，事件数量会非常高。  
第二，状态更新风暴。前端每个 chunk 都 `setState` 会造成频繁调度。  
第三，渲染风暴。流式阶段如果每次都跑 Markdown 解析，CPU 开销明显。  
这些问题叠加后，表现就是：输入延迟、滚动卡顿、页面掉帧。  
所以我优化不是只改一个点，而是“服务端降事件频率 + 前端降 setState 频率 + 渲染降级”一起做。

可补充：  
排查时我会结合浏览器 Performance 面板，看长任务、重绘和 JS 执行峰值。

## 7. 你做的“前后端双端合批”策略是什么？阈值怎么定？

主回答：  
我用的是“双阈值合批”：时间阈值 + 字符阈值。  
服务端先把 token 写入 buffer，达到字符阈值就立即发；没达到就按时间窗口发送。当前实现里服务端是 `45ms / 48 chars`。  
前端也是同样思路，先入 buffer 再 flush，当前是 `33ms / 24 chars`。  
这样做的好处是：小 token 不会引发事件风暴，大段内容又能及时刷出，不会让用户觉得卡住不动。阈值来自实际体验调优，核心目标是“看起来连续、内部不过载”。

可补充：  
阈值不是固定不变的，后续可以做成环境变量，按模型特性和机器性能调整。

## 8. 如何保证合批后不会丢失最后几个 chunk？

主回答：  
这点我专门做了收尾保护。  
因为合批用了 buffer 和 timer，如果流刚结束、定时器还没触发，尾包就可能丢。  
我的处理是：在 `done`、`error`、`abort` 这些收尾路径里都“强制 flush 一次 buffer + 清理定时器”。  
前端和服务端都做了同样策略，所以即使在异常结束场景，最后一段内容也能落地，不会出现“回答差最后一句”的问题。

可补充：  
面试官如果追问，可以补一句：这是流式系统里非常高频的边界 bug，不做显式 flush 很容易踩坑。

## 9. 为什么流式阶段先纯文本渲染，结束后再 Markdown 渲染？

主回答：  
因为流式阶段的核心诉求是“持续反馈”，不是“最终排版”。  
Markdown 解析在高频更新下成本比较高，尤其是列表、代码块、表格等内容，会不断触发重解析和重绘。  
所以我采用两阶段策略：  
第一阶段，流式中先纯文本渲染，保证轻量和流畅；  
第二阶段，流结束后再一次性做 Markdown 精渲染，保证可读性。  
这个方案是典型的“先吞吐、后精修”。

可补充：  
这样做还顺便降低了流式中异常 Markdown 导致渲染报错的概率。

## 10. 你如何验证流式优化是否生效？会看哪些指标？

主回答：  
我会从四组指标判断：  
第一组是传输指标，比如单次会话 SSE 事件数、平均 chunk 大小。  
第二组是前端指标，比如 UI flush 次数、长任务数量、掉帧情况。  
第三组是体验指标，比如首包时间、整段完成时间。  
第四组是稳定性指标，比如流式异常率、降级触发率。  
优化有效的标准是：事件和 flush 明显下降，首包时间不恶化，页面更顺滑，异常率不升高。

可补充：  
如果面试官问是否有具体数字，你可以说“看趋势和对比实验，不只看单点数据”。

## 11. 线上如果模型超时或限流，你的降级策略是什么？

主回答：  
我把降级分成三层。  
第一层是请求层：设置超时、快速失败，必要时有限重试。  
第二层是交互层：统一错误事件格式，前端给出明确提示，不让用户卡在加载态。  
第三层是体验层：允许用户继续提问，不把一次失败扩散成整个会话不可用。  
核心目标是“失败可感知、状态可恢复、流程可继续”。

可补充：  
如果是高峰期限流，优先保证核心路径可用，再考虑降级回答长度或降级到非流式返回。

## 12. Markdown 输出格式错误时，怎么兜底？会影响后续消息吗？

主回答：  
我的兜底是“这条消息失败就降级纯文本，不影响整个会话”。  
具体做法是用 `MarkdownErrorBoundary` 包裹渲染组件，渲染异常后切纯文本显示。  
同时在内容变化时重置错误状态，让后续消息可以正常尝试 Markdown。  
所以它不会把错误状态带到下一条消息，也不会导致整个聊天面板崩溃。

可补充：  
这类兜底是高可用思路：宁可显示朴素一点，也不能让用户看不到内容。

## 13. SSE 数据帧异常（比如 data 不是 JSON）怎么处理？

主回答：  
我在解析层做了容错，而不是假设服务端永远正确。  
解析时先拆 `event` 和 `data`，再尝试 JSON 反序列化；如果失败，就回退为原始文本 payload，继续流程，不直接抛出致命错误。  
这样单帧异常只影响当前帧，不会把整条流打断。  
在流式系统里，容错比“严格失败”更符合用户体验。

可补充：  
这个策略也方便排查问题，因为异常内容还能被记录和观察。

## 14. RAG 文档入库流程是怎样的？

主回答：  
我的入库流程是：文档清洗 -> 语义分块 -> 向量化 -> 写入向量库。  
清洗阶段会去掉无效噪声，保证分块质量；分块阶段按语义和长度做切分；向量化后把向量和 metadata 一起写入 ChromaDB。  
这样做的意义是把原始文档转成“可检索知识单元”，后续对话先检索相关片段，再把片段作为上下文交给模型回答，提高答案相关性和可解释性。

可补充：  
如果文档更新，会走增量重建而不是全量重建，控制成本。

## 15. 为什么采用“段落 -> 句子 -> 大小控制”的三级分块？

主回答：  
因为单一分块规则很难同时满足语义完整和长度约束。  
按段落切可以保留主题连续性；按句子细化能减少硬切断句；最后大小控制保证不超 embedding 输入限制。  
三级策略本质是在做一个平衡：既要可检索，又要尽量保留上下文语义完整性。  
这会直接影响后续召回质量。

可补充：  
面试官如果追问，你可以说“分块策略是 RAG 质量最核心的杠杆之一”。

## 16. overlap 解决了什么问题？副作用是什么？

主回答：  
overlap 主要解决“边界语义丢失”。如果不重叠，关键句可能被切断在两块之间，检索时两边都不完整。  
有 overlap 后，边界上下文会被保留，召回更稳。  
副作用是向量数量变多，存储和检索成本上升，而且可能出现重复召回。  
所以我会控制 overlap 比例，并在召回后做去重和重排。

可补充：  
一句话概括：overlap 是用可控成本换召回稳定性。

## 17. Top-K 怎么选？K 太大或太小有什么问题？

主回答：  
K 太小，关键信息可能召不回来，回答会“缺料”；K 太大，噪声会增加，还会提高 token 成本，反而影响生成质量。  
我会先基于样本集做离线评估，选一个默认 K，然后按问题复杂度或检索得分动态调整。  
核心不是追求固定最优 K，而是保证在不同问题类型下“相关片段够用但不过量”。

可补充：  
可以顺带说：K 的调整要和上下文窗口、提示词模板一起看，不是独立参数。

## 18. 召回后如何组织上下文，减少幻觉？

主回答：  
我会做三件事：  
第一，先按相关性排序和去重，只保留最有用片段；  
第二，用稳定模板拼接上下文，避免信息结构混乱；  
第三，在系统提示词里明确约束“优先基于检索内容回答，不确定就说不知道”。  
这样模型的发挥空间会被收敛，幻觉概率明显下降。

可补充：  
如果是高风险问题，还可以要求输出“依据片段”来提升可解释性。

## 19. 文档更新后，向量索引如何做增量更新与一致性保障？

主回答：  
我会用“分块级增量更新 + 版本控制”来做一致性。  
文档变化时，只重算受影响分块，不全量重建。  
写入时带文档 ID、分块 ID、版本号，采用先删旧版本再写新版本或幂等 upsert，避免新旧数据混在一起。  
这样可以在成本可控的前提下，保证检索看到的是最新、可追溯的数据。

可补充：  
如果面试官问一致性级别，你可以回答“业务上追求最终一致，关键是避免脏读和重复召回”。

## 20. ChromaDB 里存哪些 metadata？它们怎么帮助检索质量？

主回答：  
我一般会存：文档 ID、标题、分块序号、来源路径、标签、时间戳、可能还有分类信息。  
这些 metadata 有两个价值：  
第一，检索时可以做过滤和重排，比如按来源、标签、时间约束范围；  
第二，生成答案时可以回溯信息来源，提升结果可解释性。  
从工程角度看，metadata 不只是“附加字段”，它直接决定了检索控制力和后续可维护性。

可补充：  
你可以补一句：没有 metadata 的向量库很难做稳定线上检索，只能“纯相似度盲查”。
