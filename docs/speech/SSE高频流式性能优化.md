# SSE 高频流式性能优化（答辩逐字稿）

## 0. 开场

大家好，这一部分我汇报的是 SSE 高频流式返回下的前端性能优化。这个问题的本质不是 SSE 协议慢，而是数据到达太密，前端把每个小片段都当成一次完整渲染任务去处理，导致主线程被打满。

## 1. 问题定义

我先定义一下线上现象，主要有四个：

1. 用户输入时会感觉键盘延迟。
2. 聊天窗口滚动不顺滑，偶发掉帧。
3. CPU 使用率明显升高，低配机器更明显。
4. 回答越长，卡顿越严重。

当时模型是按 token 高频吐字，前端如果每收到一个 `chunk` 就立刻 `setState`，会触发大量 React commit。再叠加 Markdown 解析、语法高亮、自动滚动，渲染链路就很容易超预算。

## 2. 根因分析

我把链路拆成三段看：

1. 传输层：SSE 事件过密。
2. 状态层：每个事件都触发一次状态更新。
3. 视图层：每次更新都做重解析和重布局。

所以性能瓶颈不在“单次事件慢”，而在“事件次数过多”。优化方向就是把高频小更新，压缩成低频可控更新。

## 3. 优化方案

### 3.1 服务端批量发送

服务端不再“每 token 一发”，改成“双阈值批量发送”：

- 字符阈值：累计达到 `N` 个字符就发送。
- 时间阈值：即使字符没到，也每 `T` 毫秒至少发送一次。

并且在 `complete / error / abort` 三条结束路径上，都强制执行一次 `flush`，保证尾字不丢。

### 3.2 前端批量提交

前端接到 `chunk` 后先进入内存 buffer，不立即改 UI。

- 到字符阈值就立即提交，保证实时感。
- 没到阈值就按时间窗口批量提交，控制渲染频率。

这样 `setState` 次数会明显下降。

### 3.3 渲染分层

流式阶段只做轻量文本渲染，不做重型 Markdown 处理。回答结束后再做一次完整 Markdown 渲染。

这一步的收益很直接：把高频阶段的重计算挪到低频阶段执行。

### 3.4 只更新活跃消息

我只更新“当前正在生成的那条消息”，不遍历整条聊天历史。因为消息越多，整列表重算的成本越高，这个优化对长会话尤其重要。

## 4. 实现要点

下面是我在答辩里会强调的实现细节：

1. 服务端和前端都采用双阈值策略，避免单点失衡。
2. 所有结束路径统一走 `flushFinal()`，避免最后几段文本丢失。
3. 前端增量更新用函数式写法，避免并发更新覆盖。
4. 自动滚动节流到 `requestAnimationFrame`，避免每个 chunk 都触发布局。

可简化为一句话：传输层降频、状态层批处理、视图层轻量化。

## 5. 结果与指标

下面这组数据是我在本地压测和联调时观察到的典型结果：

| 指标                     | 优化前   | 优化后                 |
| ------------------------ | -------- | ---------------------- |
| SSE 事件数（单次长回答） | 3000+    | 300~600                |
| 前端渲染提交次数         | 2000+    | 80~200                 |
| 长任务（>50ms）          | 高频出现 | 明显下降               |
| 首字出现时间             | 快       | 基本不变（仅小幅波动） |

重点是：流畅度显著提升，但“首字可见时间”没有被明显牺牲。

## 6. 风险和兜底

我重点处理了三个风险点：

1. 过度批量导致“像卡住了”
   解决：设置时间阈值上限，确保最长等待可控。

2. 结束事件与 buffer 竞态
   解决：先 flush buffer，再更新结束状态。

3. 异常中断丢尾字
   解决：`error` 和 `abort` 也走同一套尾包补写逻辑。

## 7. 可能追问

### Q1：为什么不直接换 WebSocket？

这次瓶颈不是协议能力，而是渲染频率。即使换成 WebSocket，如果仍然每条消息都渲染，问题依旧存在。先把更新策略做对，再谈协议替换才有意义。

### Q2：阈值怎么定？

我用的是“体验优先”的调参方式：先守住首字时间，再逐步增大批量窗口，直到帧率和交互稳定。最终阈值是通过压测和真机体验共同确定的。

## 8. 总结收口

这部分我最后会这样总结：

“高频流式卡顿的根因是更新次数，不是 SSE 本身。我的做法是服务端批量发送、前端批量提交、渲染分层降载，并在所有结束路径做统一补尾。最终在不牺牲实时感的前提下，明显改善了页面流畅度和稳定性。”
