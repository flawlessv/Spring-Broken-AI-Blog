# SSE 高频流式性能优化

## Q：大模型用 SSE 高频返回时，怎么解决前端性能问题？

A：这个问题要分两步说，先说为什么会卡，再说怎么解决。

### 一、为什么会卡

本质是：更新太频繁，主线程被打满了。

1. 模型每吐一点内容就推一次 SSE 事件，事件特别密。
2. 前端如果每个 `chunk` 都立刻 `setState`，就会触发大量组件更新。
3. 如果还在流式阶段反复做 Markdown 解析、DOM 更新、滚动计算，CPU 开销会更高。
4. 结果就是：输入延迟、滚动掉帧、页面发卡。

可以把它理解成：本来应该“攒一批再处理”，你却“来一条就全流程处理一遍”，次数太多自然会卡。

### 二、怎么解决

核心思路：把很多次小更新，变成少量可控的大更新。

1. 服务端先合并再发：不要每个 token 都发，达到一定字符数就发一次；如果字符不够，也按固定时间发一次，防止页面卡太久没更新；在 `done / error / abort` 前再强制发一次，防止最后几个字丢失。
2. 前端先缓存再更新：`chunk` 先放到内存 buffer，不要立刻改 UI；达到字符阈值就立即提交，没达到就按时间间隔批量提交，避免“每来一条就 setState 一次”。
3. 只更新当前正在生成的那条消息：不要每次都遍历全部消息列表，聊天越长这个优化越重要。
4. 用数据验证效果：看事件数、前端渲染提交次数、长任务、掉帧是否下降，同时确认首字出现时间基本稳定。

### 三、可直接说的版本

“高频 SSE 卡顿的根因不是 SSE 本身，而是更新太频繁。我会在服务端做批量发送，在前端做批量更新，避免每个 chunk 都触发一次渲染；流式阶段先用纯文本保证顺滑，结束后再做 Markdown 渲染；最后在所有结束路径前强制刷新缓存，避免丢尾字。这样可以同时保证实时感和页面流畅度。”
