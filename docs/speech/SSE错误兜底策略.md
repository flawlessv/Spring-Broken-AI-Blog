# SSE 错误兜底策略（答辩逐字稿）

## 0. 开场

这一部分我汇报的是 SSE 流式输出里的异常兜底。我的目标不是把坏数据“修复成完美格式”，而是优先保证三个结果：页面不崩、内容可读、会话可继续。

## 1. 问题定义

流式场景里最常见的异常是三类：

1. JSON 片段不完整，解析报错。
2. Markdown 结构破损，渲染异常。
3. HTML 标签不闭合或包含风险标签。

如果没有分层兜底，这些问题很容易造成两种后果：

- 轻则本轮回答显示异常。
- 重则状态机被打断，输入区不可用，用户只能刷新页面。

## 2. 设计原则

我的设计原则是“逐层降级、局部失败、全局可用”：

1. 单条事件失败不能拖垮整条流。
2. 富文本失败自动回退纯文本。
3. 任何结束路径都要补尾并收口。

## 3. 兜底架构

### 3.1 收流层兜底：先拼包，再解析

SSE 是分段到达的，读取到的内容不一定正好是完整事件。

我的处理方式：

1. 用 `buffer` 累积字节流。
2. 仅按 `\n\n` 切出完整事件。
3. 不完整尾包保留到下一轮继续拼接。

这样可以避免“半包直接解析”带来的误报。

### 3.2 协议层兜底：事件级 try/catch

每条 `data:` 都独立 `try/catch`，解析失败时只降级当前事件：

1. 记录错误日志和上下文。
2. 当前条目回退为文本或跳过。
3. 后续事件继续处理，不中断主循环。

这一步保证“局部坏数据不影响全局会话”。

### 3.3 展示层兜底：富文本失败自动降级

展示策略分两级：

1. 优先走 Markdown 渲染。
2. 渲染报错则自动切换纯文本视图。

对于 HTML 内容，我默认不直接裸渲染，必须经过白名单清洗或转义，避免结构污染和安全风险。

### 3.4 结束层兜底：统一补尾

无论是 `complete`、`error` 还是用户 `abort`，统一执行：

1. 先 flush 缓存到 UI。
2. 再写入结束状态。
3. 最后释放资源。

这样不会出现“最后几句看不到”的问题。

### 3.5 交互层兜底：给用户明确出口

当系统触发降级时，我会明确提示“已降级为纯文本”，并提供“重试本轮”入口。

关键点是：失败只影响当前消息，不锁死输入框，不影响后续提问。

## 4. 三类异常的具体处理口径

### 4.1 JSON 解析失败

JSON 没有容错解析，`JSON.parse` 失败就是失败，所以必须强制 `try/catch`。

处理策略：

1. 解析失败则回退到原始文本通道。
2. 该条事件打点上报，便于排查。
3. 流程继续，等待下一条事件。

### 4.2 Markdown 结构损坏

多数渲染器有一定容错，但我不依赖渲染器“自动修复”。

处理策略：

1. 首选 Markdown 渲染。
2. 渲染异常立即降级纯文本。
3. 结束后可选触发一次完整重渲染尝试。

### 4.3 HTML 未闭合

浏览器会做一定自动纠错，但纠错结果不可控。

处理策略：

1. 默认不信任模型原始 HTML。
2. 若业务需要展示 HTML，先清洗再渲染。
3. 无法确认安全时，统一转义为文本。

## 5. 可直接复述的实现要点

我在答辩里会把实现压缩成 5 句话：

1. 流读取必须先拼完整事件，再做解析。
2. 每条事件独立容错，单条失败不影响整流。
3. 展示链路分级降级，先 Markdown，失败转纯文本。
4. 三种结束路径统一补尾，保证不丢最后内容。
5. 降级时给用户可见提示和重试入口，保障可用性。

## 6. 结果

落地后，系统行为有三个明显变化：

1. 非法数据不再触发整页异常。
2. 会话可持续，用户可以继续追问。
3. 线上问题定位更快，因为异常被结构化记录。

## 7. 追问准备

### Q1：兜底会不会掩盖真实问题？

不会。兜底是用户可用性策略，不是忽略问题。所有降级路径都会打点，开发侧仍然能追踪根因。

### Q2：为什么不直接严格校验，失败就终止？

终止策略会把一次局部错误升级成会话级故障。在对话产品里，“持续可用”优先级更高，所以采用局部降级更合理。

## 8. 总结收口

这部分我最终结论是：

“SSE 异常兜底的关键是分层处理。收流层防半包，协议层防解析崩溃，展示层做降级，结束层做补尾，交互层给重试出口。这样即使收到坏格式数据，页面也不会崩，用户仍然能稳定使用。”
