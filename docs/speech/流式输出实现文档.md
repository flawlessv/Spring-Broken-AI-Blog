# RAG 流式输出实现（答辩逐字稿）

## 0. 开场

大家好，这一部分我汇报的是 RAG 问答的流式输出实现。目标是把“等待完整答案”的时间，转成“边生成边阅读”的体验，让用户在几百毫秒内看到首屏反馈。

## 1. 先回答两个高频问题

### Q1：前端会发几次请求？

一次。前端发一个 `POST /api/ai/rag/stream`，然后持续读取响应流。

### Q2：后端是响应多次吗？

从 HTTP 语义看是“一次响应”，但响应体是分段持续写出的，所以用户看到的是持续更新。

## 2. 为什么选 SSE

### 什么是 SSE？

SSE（Server-Sent Events）是一种基于 HTTP 的服务器推送技术。它允许服务器在一个 HTTP 响应中持续向客户端推送数据，而不需要客户端反复发起请求。

### SSE 的响应头

SSE 需要设置特定的响应头，告诉浏览器这是一个流式响应：

- `Content-Type: text/event-stream` 告诉浏览器这是 SSE 流
- `Cache-Control: no-cache` 禁止缓存，确保每次都是最新数据
- `Connection: keep-alive` 保持连接打开
  我的场景是“服务端单向推送”，所以 SSE 比 WebSocket 更贴合：

1. 协议简单，直接基于 HTTP。
2. 服务端只需按事件格式持续写入。
3. 和现有网关、日志链路更容易对接。

补充一个常见误解：SSE 在 HTTP/1.1 和 HTTP/2 都可用。区别在于传输复用机制，不影响我们“同一响应持续下发事件”的编程模型。

## 3. 事件协议设计

我定义了四类事件：

1. `sources`：检索完成后立即返回参考来源。
2. `chunk`：模型生成的增量文本。
3. `complete`：本轮完成信息。
4. `error`：异常信息。

事件格式保持标准 SSE 结构：

```text
event: chunk
data: {"chunk":"..."}

```

双换行 `\n\n` 作为事件边界。

## 4. 整体分层

我把实现拆成四层，职责清晰：

1. 前端层：发请求、读流、解析事件、更新 UI。
2. API 路由层：创建 `ReadableStream`，把内部回调转成 SSE。
3. RAG 层：检索上下文、组织 prompt、调模型流式接口。
4. AI 客户端层：对接模型 SDK，逐块读取内容。

这种分层的好处是：替换模型或替换前端协议时，只改局部层，不会牵动全链路。

## 5. 关键实现主线

### 5.1 AI 客户端：开启模型流式返回

在模型调用侧设置 `stream: true`，通过异步迭代逐块读取增量文本，每拿到一段就通过回调抛给上层。

### 5.2 RAG 层：先检索再流式生成

我在 RAG 层做了一个体验优化：

1. 先完成向量检索。
2. 立刻回调 `sources` 给前端。
3. 再进入模型流式生成。

这样用户能先看到“答案依据来自哪里”，再看答案逐步展开。

### 5.3 API 路由层：将回调封装成 SSE

路由层做两件事：

1. 设置 SSE 响应头：`Content-Type: text/event-stream`。
2. 把 `onSources/onChunk/onComplete/onError` 统一编码成 `event + data` 格式下发。

并在 `complete` 与 `error` 路径都显式 `close`，避免悬挂连接。

### 5.4 前端层：buffer 防半包

前端读取流时不能假设“每次 read 都是完整事件”。我的处理方式是：

1. 用 `buffer` 累积文本。
2. 按 `\n\n` 切出完整事件。
3. 不完整尾包保留到下一次拼接。

这是流式解析稳定性的关键。

## 6. 性能与体验优化

### 6.1 批量提交 UI

如果 `chunk` 频率很高，前端会渲染过密。我采用“先缓冲再提交”的策略，降低状态更新次数，避免掉帧。

### 6.2 提前显示来源

`sources` 提前发送可以显著降低用户等待焦虑，尤其是回答较长时，用户能先判断答案可信度。

### 6.3 异常不阻断输入

任一流式异常都只影响当前轮次，输入框保持可用，用户可以立即重试或继续追问。

## 7. 结果指标

这套方案带来的核心收益可以归纳为三条：

1. 首屏反馈更快，用户几乎立即看到系统在工作。
2. 感知延迟更低，等待时间被阅读时间替代。
3. 参考来源展示更早，答案可解释性更强。

## 8. 风险点与处理

### 8.1 网络中断

策略是中断即收口：停止读取、保留已接收内容、提示用户重试。本期未做自动断点续传，保证复杂度可控。

### 8.2 事件解析失败

单条事件失败只丢当前条，不中断整流，并记录日志用于定位上游数据问题。

### 8.3 高频 chunk 卡顿

通过双阈值批量提交降低渲染频率，并在结束路径执行强制 `flush` 保证尾包不丢。

## 9. 追问准备

### Q1：为什么不用 WebSocket？

当前场景只需要服务端到客户端单向推送，SSE 成本更低、实现更直接。若未来有“边生成边打断并发控制”等双向诉求，再升级 WebSocket 更合理。

### Q2：SSE 能否承载生产流量？

可以，但要关注网关超时、代理缓冲和心跳策略。只要基础设施参数配好，SSE 在问答流式场景完全可用。

### Q3：前端为什么不用 EventSource？

`EventSource` 只支持 GET，不方便携带复杂请求体。当前采用 `fetch + ReadableStream`，可继续使用 POST 并保持解析可控。

## 10. 收口总结

这部分我最后会这样总结：

“我把流式输出拆成四层：模型层产出增量、RAG 层组织语义、路由层封装 SSE、前端层稳定解析。通过 sources 提前下发、chunk 增量渲染和异常统一收口，实现了稳定可维护的 ChatGPT 式流式体验。”
