# 智能虚拟列表组件

## 一、项目背景与问题（1分钟）

在业务场景中，我们遇到了一个典型的性能问题：费用列表数据量非常大，比如10万条记录，这导致了三个严重的性能瓶颈：

- **第一个问题**：接口会超时，一次性请求10万条数据，响应时间长达几十秒甚至超时
- **第二个问题**：页面卡顿，10万个DOM节点占用大量内存，滚动帧率低于10FPS
- **第三个问题**：资源浪费，用户可能只看前40条，但请求了全部10万条

针对这些问题，我设计并实现了一个**智能虚拟列表组件**，核心策略是：**虚拟滚动 + LRU缓存 + 智能预加载 + 批量加载**。

最终的效果是：支持10万条数据流畅滚动（60FPS），DOM节点从10万降到20-30个（减少99.97%），内存占用从200MB降到5MB（减少97.5%），请求次数从10万次降到2500次（减少97.5%）。

## 二、核心难点与解决方案（5-7分钟）

接下来我讲一下在这个过程中遇到的三个核心难点，以及我是怎么解决的。

### 难点1：如何解决海量DOM渲染导致的性能问题？

**先说一下为什么10万DOM节点会导致卡顿**：

浏览器渲染一个页面需要经过几个步骤：DOM树构建 → 样式计算 → 布局（Layout） → 重绘（Paint） → 合成（Composite）。

当页面有10万个DOM节点时：

1. **DOM树构建慢**：10万个节点需要创建大量对象，每个对象占用内存，首屏渲染时间5-10秒
2. **内存占用高**：每个DOM节点包含属性、样式、事件监听器等，10万个节点内存占用超过200MB
3. **布局计算慢**：浏览器需要计算每个元素的位置和大小，节点越多计算时间越长
4. **滚动时频繁重排重绘**：每次滚动都会触发布局和重绘，10万个节点导致滚动帧率低于10FPS

**解决方案**：我采用了**虚拟滚动技术**，核心思想很简单：**只渲染用户能看到的20-30个DOM节点**。

具体实现上，我使用了 `@tanstack/react-virtual` 库：

```typescript
// 获取ID列表（轻量级）
const [ids, setIds] = useState([]);
useEffect(() => {
  fetch("/api/ids")
    .then((res) => res.json())
    .then(setIds);
}, []);

// 配置虚拟滚动
const rowVirtualizer = useVirtualizer({
  count: ids.length, // 总数据量
  estimateSize: () => 50, // 每行高度
  overscan: 5, // 上下各多渲染5条作为缓冲
});
```

渲染时使用绝对定位 + transform：

```typescript
<div style={{
  position: 'absolute',
  transform: `translateY(${virtualItem.start}px)`,
  height: `${virtualItem.size}px`,
}}>
  {item ? <RowData data={item} /> : <Skeleton />}
</div>
```

为什么要这样设计？

- **绝对定位**：不需要频繁调整DOM结构，只需要计算transform值，浏览器性能更好
- **transform**：使用GPU加速，不触发layout，只触发composite，性能更好
- **缓冲区**：上下各预渲染5条，用户滚动时新的item已经准备好了，避免出现空白

**效果**：DOM节点从10万降到20-30个，首屏渲染从5-10秒降到500毫秒以内，滚动帧率从低于10FPS提升到稳定60FPS。

### 难点2：虚拟列表解决了DOM渲染问题，但数据从哪里来？

**先说一下我遇到的问题**：

虚拟列表只解决了渲染问题，但还需要决定"应该加载哪些数据"。

最简单的做法是**普通懒加载**：首屏加载第1-40条，滚动到第35条时，加载第41-80条，从上往下慢慢分批加载。

但这种方式有个致命问题：**用户不会老老实实从上往下滚动**。

实际场景中，用户可能：

- 直接拖动滚动条从第1条跳到第5000条
- 使用搜索功能跳转到中间某个位置
- 快速滚动跳过大量数据

这时候普通懒加载就不行了，因为中间的数据都没加载过，我不可能把用户跳过的几千条都加载一遍，这会导致大量并发请求不需要的资源，既浪费时间又浪费网络带宽。

**解决方案**：我设计了一个**智能加载策略**，核心思路是：**优先加载当前可视区的数据，然后再向滚动方向扩展预加载**。

举个例子：用户直接跳到第5000条，虚拟列表库会告诉我当前显示的是第5000-5020条。那我就会：

1. 先检查这20条里面哪些没有缓存，优先加载它们
2. 然后向滚动方向继续收集，凑够40条一起请求

**实现分三步**：

**第一步：判断滚动方向**

有三种方法：

1. **基于scrollTop变化**（我采用的方案）

```typescript
const handleScroll = () => {
  const currentScrollTop = container.scrollTop;
  if (currentScrollTop > lastScrollTop) {
    scrollDirection = "down";
  } else {
    scrollDirection = "up";
  }
  lastScrollTop = currentScrollTop;
};
```

优点：兼容性好（支持鼠标、触屏、键盘），实现简单

2. **基于wheel事件**

```typescript
const handleWheel = (e: WheelEvent) => {
  if (e.deltaY > 0) {
    scrollDirection = "down"; // 向下滚动
  } else {
    scrollDirection = "up"; // 向上滚动
  }
};
```

优点：响应更快，可以在滚动发生前预知方向，适合预加载优化
缺点：仅支持鼠标滚轮，触屏设备不支持

3. **基于虚拟列表库API**

```typescript
const virtualizer = useVirtualizer({
  count: ids.length,
  getScrollElement: () => parentRef.current,
});

// 通过 virtualizer 的状态变化推断方向
const lastRangeRef = useRef({ start: 0, end: 0 });
useEffect(() => {
  const currentRange = {
    start: virtualizer.range?.startIndex ?? 0,
    end: virtualizer.range?.endIndex ?? 0,
  };
  const lastRange = lastRangeRef.current;

  if (currentRange.start > lastRange.start) {
    scrollDirection = "down";
  } else if (currentRange.start < lastRange.start) {
    scrollDirection = "up";
  }
  lastRangeRef.current = currentRange;
}, [virtualizer.range]);
```

优点：更符合虚拟列表的语义，通过可视范围的变化判断方向
缺点：依赖具体的虚拟列表库，通用性较差

我选择方法1的原因是兼容性最好，实现最简单。

**第二步：确定检查范围并收集未缓存ID**

我设计了一个触发阈值机制，不是每次滚动都触发请求，而是只在接近未缓存边界时才触发。

为什么要设计阈值呢？因为如果每次滚动都触发请求，会导致请求过于频繁。我设置阈值为约5条（pageSize的1/8），只有当可视区接近未缓存边界时才触发请求。

```typescript
const threshold = Math.floor(pageSize / 8); // 触发阈值，约5条

// 根据滚动方向确定检查范围
if (scrollDirection === "down") {
  // 向下滚动：检查可视区 + 底部阈值
  checkStart = visibleStart;
  checkEnd = Math.min(ids.length, visibleEnd + threshold);
} else if (scrollDirection === "up") {
  // 向上滚动：检查顶部阈值 + 可视区
  checkStart = Math.max(0, visibleStart - threshold);
  checkEnd = visibleEnd;
}
```

收集策略是：**先收集可视区内的未缓存ID，如果不够40条，再向滚动方向继续收集**。

这里有一个关键设计是**边界限制**，确保不会越界收集错误方向的数据。

举个例子说明边界限制的作用：

假设用户向上滚动到位置100-107，其中100-104已缓存，105-107未缓存。

收集流程：

- 第一步：收集可视区100-107（边界限制在107）
  → 只收集到105、106、107（3个）
- 第二步：不够40个，向上扩展
  → 从99向前收集37个
- 结果：[63-99] + [105-107] = 40个，全部是正确方向的数据

如果没有边界限制，从100向后搜索时，会跳过已缓存的100-104，继续收集108、109...，这样就收集了向下方向的数据，但用户在向上滚动！

**第三步：批量请求并写入缓存**

```typescript
const fetchAndCacheData = async (items) => {
  const idsToFetch = items.map((item) => item.id);
  idsToFetch.forEach((id) => loadingSet.add(id)); // 先标记为加载中

  const itemsData = await getItems({ ids: idsToFetch });
  itemsData.forEach((item) => setData(item.id, item));

  idsToFetch.forEach((id) => loadingSet.delete(id)); // 清除加载状态
};
```

**效果**：用户快速滚动时空白率从30%降低到5%以下，加载体验非常流畅。

### 难点3：如何避免重复请求和控制内存？

**先说一下我遇到的问题**：

有了智能加载策略后，在实际使用中又发现了新问题：

1. **来回滚动时重复请求相同数据**：用户从第1条滚到第1000条，又滚回第950条，这时候第950条的数据之前请求过，但可能已经不在缓存里了，又要重新请求
2. **加载状态频繁闪烁**：每次滚动都触发加载，skeleton一直出现又消失
3. **内存占用越来越高**：如果把所有请求过的数据都缓存起来，用户滚得越远，缓存越大，最后可能占用几百MB内存

**解决方案**：我设计了一个**LRU智能缓存**来解决这个问题。

**为什么选择LRU？**

LRU（Least Recently Used，最近最少使用）的核心思想是：淘汰最近最少使用的数据。

选择LRU的原因：

- **符合用户行为**：用户滚动时最近看到的数据很可能再次访问，比如来回滚动查看对比，而最久未看到的数据很可能不会再访问
- **性能优秀**：所有操作（get、set、delete）都是O(1)时间复杂度，实现简单
- **内存可控**：缓存大小固定（默认1000条），自动清理，不会内存泄漏

相比之下：

- FIFO（先进先出）：可能淘汰用户正在查看的数据，导致频繁重新加载
- LFU（最不经常使用）：需要维护访问频率，实现复杂，且在滚动场景中不如LRU合适

**具体实现**：利用JavaScript Map的有序性特点

Map会按照插入顺序保存键值对，所以我可以用它来实现LRU：

- 最近使用的数据保留在缓存末尾
- 最久未使用的数据排在缓存开头
- 缓存满时淘汰开头的数据

```typescript
// 访问数据时：删除后重新插入，移到末尾（标记为最近使用）
const getData = (id) => {
  const item = cache.get(id);
  if (item) {
    cache.delete(id);
    cache.set(id, item); // 重新插入，移到末尾
  }
  return item;
};

// 写入数据时：容量满时删除第一个（最久未使用）
const setData = (id, item) => {
  if (cache.size >= maxSize) {
    const oldestKey = cache.keys().next().value;
    cache.delete(oldestKey);
  }
  cache.set(id, item);
};
```

**加载状态追踪**：

除了缓存，我还设计了**加载状态追踪**来避免重复请求。当收到一批要请求的ID后，我会先把它们标记为loading状态，这样在请求返回之前，如果用户又滚动到这些位置，就不会重复发起请求。

```typescript
const fetchAndCacheData = async (items) => {
  const idsToFetch = items.map((item) => item.id);
  idsToFetch.forEach((id) => loadingSet.add(id)); // 先标记为加载中

  const itemsData = await getItems({ ids: idsToFetch });
  itemsData.forEach((item) => setData(item.id, item));

  idsToFetch.forEach((id) => loadingSet.delete(id));
};
```

状态判断逻辑：

| 状态     | hasData | isLoading | 操作               |
| -------- | ------- | --------- | ------------------ |
| 已缓存   | ✅      | ❌        | 直接使用           |
| 正在加载 | ❌      | ✅        | 不加载（避免重复） |
| 需要加载 | ❌      | ❌        | 加入批量请求       |

**效果**：来回滚动时缓存命中率超过90%，接口调用频率降低80%以上，用户体验流畅，加载状态很少出现。

## 三、为什么不用React Query？（技术亮点）

在面试中，面试官可能会问：为什么不用React Query？

React Query虽然是一个优秀的数据获取库，但在虚拟滚动场景下有一些局限性：

**1. 不支持智能部分缓存**

React Query的缓存基于完整queryKey：

```typescript
// 第一次请求
queryKey: ["items", [1, 2, 3, 4]]; // 缓存了 id: 1,2,3,4 的数据

// 第二次请求
queryKey: ["items", [2, 3, 4, 5]]; // 期望：重用 2,3,4，只请求 5
```

实际情况是，`['items', [1,2,3,4]]` 和 `['items', [2,3,4,5]]` 是两个完全不同的缓存键，第二次请求会重新获取2、3、4、5的所有数据，不会重用已缓存的2、3、4，导致大量重复请求。

**2. 双向滚动场景的并发问题**

向下滚动的时候，useInfiniteQuery的"加载更多"模式可以正常工作，但向上滚动需要加载之前的数据，React Query没有内置的"加载更少"机制，从下往上滚会触发很多次单个ID的请求，导致大量接口并发。

**3. 无法精确控制加载范围**

我们的场景需要根据滚动位置动态计算需要加载的数据范围，每次请求当前行前后未被请求的20条数据，而不是固定的"下一页"，还需要智能识别已缓存的数据避免重复请求。React Query的useInfiniteQuery更适合分页场景，不太适合虚拟滚动的随机访问模式。

**4. 缓存策略不够灵活**

React Query的缓存策略基于查询key，我们的场景需要基于索引范围的精细控制，自实现LRU缓存更符合滚动场景的访问模式。

## 四、架构设计（1分钟）

我采用了清晰的三层架构，职责分离：

```
┌─────────────────────────────────────┐
│         UI 层                        │
│  - 虚拟滚动容器                       │
│  - 滚动事件监听 & 方向判断            │
└─────────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────────┐
│    数据加载层                        │
│  - 计算加载范围                       │
│  - 两步收集ID（可视区 + 方向扩展）     │
│  - 批量请求接口                       │
└─────────────────────────────────────┘
              │
              ▼
┌─────────────────────────────────────┐
│      缓存层                          │
│  - LRU缓存管理                       │
│  - 加载状态追踪                      │
└─────────────────────────────────────┘
```

数据流：

```
用户滚动 → UI层判断方向 → 数据加载层收集ID → 批量请求 → 缓存层写入 → UI重新渲染
```

这个架构的优势：

- **职责清晰**：每一层只负责自己的事情，便于维护和测试
- **可扩展性强**：可以轻松替换数据源或修改加载策略
- **可复用性高**：每个Hook都可以独立使用

## 六、可能的追问与回答

### Q1：为什么选择LRU而不是其他缓存策略？

LRU最符合列表滚动场景：用户来回滚动时，最近看到的数据很可能再次访问。相比之下，FIFO可能淘汰用户正在查看的数据，LFU实现复杂且在滚动场景中不如LRU合适。

### Q2：pageSize是如何选择的？

需要权衡单次请求时间和加载量。我默认设置40是在常见场景下的平衡值，既能减少请求次数（相比单条减少97.5%），又不会让单次请求时间太长（通常小于1秒）。可以根据数据大小和网络状况动态调整。

### Q3：虚拟滚动有什么局限性？

1. 需要固定或可预测的行高，动态高度需要额外处理
2. 不适合复杂交互（如多选、批量编辑）
3. 滚动到指定位置需要额外处理
4. 不适合数据频繁变化的场景

### Q4：如果后端不支持批量接口怎么办？

方案1：前端并行请求 `Promise.all(uncachedIds.map(id => fetchItem(id)))`，虽然不如真正的批量接口快，但比串行请求快很多
方案2：建议后端增加批量接口，在大数据量场景下几乎是必需的，可以在技术评审时提出这个需求

### Q5：这个方案的适用场景？

**适合的场景**：

- 大数据量列表（1万条以上）
- 数据不会频繁变化（或者变化后可以接受短暂的不一致）
- 用户主要是浏览数据（而不是频繁编辑）
- 需要流畅的滚动体验

**不适合的场景**：

- 数据量很小（虚拟滚动的优势不明显，反而增加复杂度）
- 数据频繁变化（缓存会频繁失效）
- 需要对列表进行复杂操作（比如多选、批量编辑、拖拽排序）
- 需要实时更新数据（比如聊天记录、股票行情）
